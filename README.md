# Мини CRM «Объекты и задачи»

React + TypeScript + Supabase. Постановщик управляет объектами и задачами; исполнитель видит свои задачи и объекты с ними. Переходы статусов и запись истории выполняются в базе.

## Запуск

1. Создайте проект Supabase. В **Authentication → Providers → Email** отключите **Allow new users to sign up**. Подтверждение email для пользователей демо сделайте вручную.
2. Выполните `supabase/migrations/20261103000000_initial.sql` в SQL Editor (или примените миграцию через Supabase CLI).
3. В **Authentication → Users** вручную создайте минимум троих пользователей: `manager@example.com`, `worker1@example.com`, `worker2@example.com`. Задайте каждому отдельный пароль. Не храните пароли в репозитории.
4. Выполните `supabase/seed.sql` в SQL Editor. Если использовали другие email, сначала замените их в файле. Скрипт создаст профили, три объекта и пять задач в разных статусах. Запускайте его один раз: повторный запуск создаст новые демо объекты.
5. Скопируйте `.env.example` в `.env` и вставьте **Project URL** из окна **Connect** и **publishable key** из **Settings → API Keys**. Переменная в коде называется `VITE_SUPABASE_ANON_KEY`, но принимает актуальный publishable key (`sb_publishable_...`). Не вставляйте `service_role` или secret key.
6. `npm install && npm run dev`. Для проверки сборки: `npm run build`.

## Проверки и структура фронтенда

Каждый компонент находится в собственной папке `src/components/<ИмяКомпонента>` и экспортируется через её `index.ts`. Стили компонента лежат рядом в `*.module.scss`. Общие классы интерфейса собраны в `src/styles/ui.module.scss`, цвета, радиусы и точки адаптивной верстки — в `src/styles/_variables.scss`, глобальные сбросы — в `src/styles/global.scss`. Компоненты и функции написаны стрелочными выражениями.

Alias `@/` указывает на `src/` в TypeScript, Vite и SCSS. Импорты между папками используют alias; импорты соседних файлов остаются относительными.

Роли, статусы, названия экранов, таблиц и вызовов Supabase собраны в `src/constants.ts`. Типы ролей и статусов выводятся из этих констант.

Клиент Supabase создаётся один раз в `src/lib.ts`. `src/api/crm.ts` содержит запросы и изменения данных; `src/hooks/useAuth.ts`, `useCrmData.ts` и `useTaskHistory.ts` управляют сессией, данными CRM и историей задачи. Компоненты не обращаются к Supabase напрямую.

Формы входа, объекта, задачи и возврата на доработку используют React Hook Form. Проверяются обязательные поля, формат email, длина текста и выбор существующего объекта и исполнителя. Ошибки показываются рядом с полями; база дополнительно проверяет права и переходы статусов.

- `npm run lint` — ESLint для TypeScript/React и Stylelint для SCSS.
- `npm run format` — форматирование Prettier.
- `npm run check` — линтеры, проверка форматирования и сборка.

Husky запускает `npm run check` перед каждым коммитом. Хук устанавливается автоматически после `npm install` через скрипт `prepare`.

## Публикация

Разместите репозиторий на GitHub. На Vercel или Netlify импортируйте его как Vite проект; команда сборки `npm run build`, папка результата `dist`. Укажите там `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Для входа передайте проверяющим URL приложения и пароли тестовых пользователей по согласованному защищённому каналу. Открытая регистрация выключена в настройках Supabase.

## Как это работает

Постановщик создаёт стройки и задачи, назначает исполнителя и принимает результат. Исполнитель видит только назначенные ему задачи и те стройки, где у него есть задачи. Он берёт задачу в работу и отправляет на проверку. Постановщик принимает задачу либо возвращает её с обязательным объяснением. В карточке каждой задачи видны все смены статуса, их авторы и время.

Правила доступа заданы в базе данных. Поэтому исполнитель не увидит чужую задачу даже при прямом обращении к Supabase, не сможет создать или удалить объект, переназначить себе задачу, принять результат или изменить историю. База также отклонит переход статуса, которого нет в процессе. Секретный ключ базы не используется в браузере.

## Решения и допущения

- Роли назначаются администратором вручную в таблице `profiles`; публичной регистрации и экрана управления пользователями нет.
- Исполнитель видит объект, если ему назначена хотя бы одна задача в этом объекте. После переназначения последней задачи объект исчезает из его списка.
- Постановщик может менять поля задачи и переназначать исполнителя в любом статусе, но статус меняет только через разрешённый переход. При удалении задачи или объекта связанная история удаляется вместе с ними; отдельно изменить или удалить запись истории через API нельзя.
- Начальное создание задачи фиксируется в истории как переход в «Новую».
- Отдельная загрузка файлов и уведомления не предусмотрены заданием.

## Проверка правил

После создания демо пользователей войдите под каждым из них. У первого исполнителя должны быть видны его три задачи, у второго — две. Попробуйте через REST API с JWT исполнителя запросить чужую задачу: RLS вернёт пустой результат. Прямой `update` статуса и `insert/update/delete` истории отклоняются правами базы. `transition_task` разрешает только допустимые переходы, а для возврата на доработку требует непустой комментарий.
